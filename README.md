# Meet-Up

> **멀리 사는 사람들도 쉽게 약속을 정하고, 함께 갈 장소부터 각자의 귀가 경로와 정산까지 한 번에 관리하는 모임 서비스**

Meet-Up은 여러 지역에 흩어져 있는 사람들이 모임을 준비할 때 발생하는 장소 선정과 이동 경로 확인, 비용 정산의 번거로움을 줄이기 위해 만든 웹 애플리케이션입니다. 참여자의 출발 위치를 바탕으로 모임 장소를 탐색하고 투표로 결정한 뒤, 모임이 끝난 후 각자의 귀가 대중교통 경로와 막차 정보를 확인하고 정산까지 이어갈 수 있도록 구성했습니다.

- **프로젝트 상태:** 중단
- **Repository:** [zuzusnasna/Meet-Up](https://github.com/zuzusnasna/Meet-Up)

## 프로젝트 개요

| 항목 | 내용 |
| --- | --- |
| 프로젝트명 | Meet-Up |
| 목표 | 모임 장소 결정, 귀가 경로 확인, 비용 정산을 한곳에서 제공 |
| 주요 사용자 | 서로 다른 지역에 거주하는 3명 이상의 모임 참여자 |
| Backend | Java 21, Spring Boot |
| Frontend | React, Vite |
| Database | Oracle Database |
| Cache | Redis |
| 외부 서비스 | Kakao Map/대중교통 경로 API, OAuth2 로그인 제공자 등 |

### 기획 배경

여러 사람이 만날 때는 각자의 출발 위치를 고려해 장소를 정하고, 참여자들의 의견을 모으고, 모임이 끝난 뒤 집으로 돌아갈 수 있는 경로와 막차 시간까지 따로 확인해야 합니다. 비용을 나누는 과정도 별도로 진행되는 경우가 많습니다.

Meet-Up은 이 과정을 하나의 흐름으로 연결해 **모임 전 장소 결정부터 모임 후 귀가와 정산까지** 지원하는 것을 목표로 합니다.

## 주요 기능

### 1. 모임방 및 참여자 관리
- 모임방 생성 및 참여
- 초대 정보를 통한 참여자 연결
- 참여자별 출발 위치 등록 및 확인
- 지도에서 참여자의 위치를 마커로 표시
- 마커에 마우스를 올리면 참여자 정보 확인
- 참여자나 장소 후보를 선택하면 지도에서 해당 위치로 이동

### 2. 모임 장소 탐색 및 투표
- 참여자 출발 위치를 바탕으로 중간 지점 탐색
- 지도에서 장소 검색 및 후보 확인
- 모임 장소 후보 등록 및 선택
- 후보별 투표를 통한 최종 약속 장소 결정
- 최종 장소 주변의 편의시설과 장소 정보 탐색

### 3. 귀가 대중교통 경로 및 막차 확인
- 최종 약속 장소에서 각 참여자의 출발지(귀가 목적지)까지 경로 조회
- **최단 시간 / 최소 환승** 기준으로 경로 조회
- 경로를 도보·지하철·버스 등의 구간으로 나누어 표시
- 구간별 이동 정보와 환승 흐름 확인
- 지하철 경로의 막차 정보를 기존 막차 조회 로직과 연결
- 새로고침을 통한 경로 정보 재조회

> 경로와 막차 정보는 외부 API에서 제공하는 경로·운행 데이터에 영향을 받습니다. 모든 경로 조합과 운행 조건에서 동일한 수준의 정보를 제공하도록 계속 보완하고 있습니다.

### 4. 비용 정산
- 모임 목적과 지출 항목에 따른 정산 정보 입력
- 참여자별 부담 금액 계산
- 모임 장소 결정 이후 정산 단계로 이어지는 화면 구성

## 핵심 구현 내용

### 모임 장소 결정 흐름

1. 모임방을 생성하고 참여자를 연결합니다.
2. 참여자별 출발 위치를 등록합니다.
3. 지도에서 중간 지점과 장소 후보를 확인합니다.
4. 참여자들이 후보에 투표합니다.
5. 투표 결과를 바탕으로 최종 약속 장소를 결정합니다.

### 귀가 경로 조회 흐름

1. 최종 약속 장소를 귀가 경로의 출발점으로 사용합니다.
2. 참여자별 등록 위치를 귀가 목적지로 사용합니다.
3. 선택한 기준(최단 시간 또는 최소 환승)에 맞춰 경로를 조회합니다.
4. 응답 경로를 구간별로 정리해 도보·대중교통 이동 흐름을 표시합니다.
5. 지하철 구간에 기존 막차 조회 로직을 연결해 막차 정보를 확인할 수 있도록 합니다.

### 조회 성능과 사용자 경험

- Redis 캐시를 활용해 동일한 경로 요청의 반복적인 외부 API 호출을 줄이도록 구성했습니다.
- 사용자가 경로 기준을 변경하면 해당 기준으로 다시 조회하도록 처리했습니다.
- 새로고침 요청 시 캐시된 결과만 그대로 보여 주지 않고 경로를 다시 확인하도록 개선했습니다.
- 출발점과 도착점, 환승 구간을 명확히 구분하고 안내 문구와 역 이름을 정규화해 경로 정보를 읽기 쉽게 개선하고 있습니다.

## 개발 중 어려웠던 점

### 환승 경로를 포함한 막차 계산

이번 프로젝트에서 특히 어려웠던 부분은 **환승이 포함된 귀가 경로에서 막차 정보를 계산하고 사용자에게 이해하기 쉽게 전달하는 과정**이었습니다.

단순히 출발역이나 도착역의 막차 시간 하나를 표시하는 것만으로는 실제 귀가 가능 여부를 판단하기 어렵습니다. 경로가 여러 지하철 노선으로 이어질 경우, 각 구간의 노선과 역, 환승 지점, 이동 순서를 연결해서 확인해야 합니다. 첫 번째 노선의 막차를 탈 수 있더라도 환승역에 도착했을 때 다음 노선의 막차가 이미 종료됐다면 전체 경로로는 귀가할 수 없기 때문입니다.

또한 경로 API에서 제공하는 구간 정보와 막차 정보의 데이터 형식·기준이 항상 일치하는 것은 아니어서, 역 이름과 노선 정보를 정규화하고 구간별 데이터를 연결하는 작업도 필요했습니다. 운행 요일에 따라 제공되는 정보가 달라지거나 일부 운행 정보가 누락되는 경우까지 고려해야 했습니다.

이를 해결하기 위해 경로를 하나의 문자열이나 단일 역 정보로 처리하지 않고 **구간별 이동 정보와 환승 흐름을 기준으로 다루도록 구조를 정리하고, 기존 막차 조회 로직과 연계하는 방향**으로 구현을 진행했습니다. 이 과정에서 외부 API의 데이터 구조를 이해하는 것뿐 아니라, 실제 사용자가 환승을 포함한 경로로 귀가할 수 있는지 판단하는 문제는 단순한 시간 조회보다 훨씬 복잡하다는 점을 배웠습니다.

### 외부 API 응답을 화면에 맞게 정리하기

외부 API에서 반환한 경로를 그대로 출력하면 역 이름이 중복되거나 도보 안내가 어색하게 표시되는 등 사용자 입장에서 이해하기 어려운 경우가 있었습니다. 이에 역 이름과 안내 문구를 정리하고, 이동 구간별 표시와 시작점·도착점의 의미를 명확히 구분하도록 개선하고 있습니다.

### 캐시와 최신 정보의 균형

대중교통 경로는 외부 API 호출 비용과 응답 시간을 고려해 캐싱할 필요가 있지만, 사용자가 경로 기준을 바꾸거나 최신 경로를 요청하는 경우에는 기존 캐시를 그대로 사용하면 기대한 결과를 제공하지 못할 수 있습니다. 따라서 일반 조회와 새로고침 요청을 구분하고, 기준별 조회 결과가 올바르게 반영되도록 개선했습니다.

## 실행 환경

### 사전 준비
- Java 21
- Node.js 및 npm
- Oracle Database
- Redis
- Kakao API 및 사용하는 외부 서비스의 인증 키

### Backend

프로젝트 루트에서 실행합니다.

```bash
# Windows
gradlew.bat bootRun

# macOS / Linux
./gradlew bootRun
```

### Frontend

```bash
cd frontend
npm install
npm run dev
```

### 환경 변수

인증 키와 접속 정보는 저장소에 직접 기록하지 말고 루트의 `.env` 파일 또는 실행 환경 변수로 관리합니다. 프로젝트 설정에서 사용하는 주요 값은 다음과 같습니다.

```dotenv
KAKAO_REST_API_KEY=
KAKAO_CLIENT_SECRET=
NAVER_CLIENT_ID=
NAVER_CLIENT_SECRET=
GOOGLE_CLIENT_ID=
GOOGLE_CLIENT_SECRET=
TOUR_API_KEY=
TAGO_SERVICE_KEY=

# Oracle 및 Redis 접속 정보는 application.properties 설정에 맞게 구성
REDIS_HOST=localhost
REDIS_PORT=6379
```

Oracle 접속 정보는 `src/main/resources/application.properties`의 데이터베이스 설정과 실제 개발 환경에 맞게 구성해야 합니다. OAuth2 공급자별 콘솔에서도 로컬 실행 주소에 맞는 Redirect URI를 등록해야 합니다.

- 환승이 포함된 대중교통 경로에서 구간별 운행 조건을 고려해야 하는 이유
- Redis 캐싱과 최신 데이터 재조회 사이의 균형
- 장소 결정부터 귀가 경로와 정산까지 이어지는 사용자 흐름 설계
